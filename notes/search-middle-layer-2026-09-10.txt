WHAT CHANGED
------------
1  Every row carries its province, Thai and Latin, in both indexes. On the
   site it is intuited from the code the row already carries — zero bytes
   added. On the edge (/api/v1) it is written into the row's search blob.
2  A city name in the query is a filter: it narrows to that province and is
   a removable chip. It is never two more words a name has to contain. Both
   engines. A query naming both cities lifts neither.
3  A held record (no pin, two facts or fewer) is in the index on its name
   and province alone. A shelf word cannot reach it, it files behind every
   row that can say more, and typing its name finds it however the rest is
   phrased. The side file of exact names is retired.
4  The state family of tags (phone held, Facebook held, website held, hours
   held, thin entry, not pinned, no contact, name only, multi-source) no
   longer reaches a reader: not on result rows, not in the second line, not
   in the refine drawers, not on place pages. It stays on the record, on
   tags.html and in the API.
5  The instant a query exists the baked pills come off and a thin bar under
   the box says the answer is coming. /api/v1 is asked in parallel and its
   rows are drawn in about 0.3 s, name and reading only; the full engine
   repaints when the index lands. Not for a where-question; never on a zero
   from the edge.
6  Nothing found hides the refine rail and the sponsor box. The shelves and
   "tell the ants" stay.
7  The province word on a list that spans both cities read a field no row
   had. It reads the one every row has.
9  FOUND ON THE WAY, AND FIXED: "nearest first" was not. Since the index
   was split in two on 9/8 the pins travel in the second file, and the page
   answered from the first without waiting — so every distance was null,
   the rail's default nearest-first order was the match order, and a row
   never printed its metres. The page now waits for the pins before it

  the tambon. The polygons on this disk since 9/8 are OCHA's COD-AB set,
  drawn by the Royal Thai Survey Department; licence verified tonight through
  the HDX record: CC BY-IGO, attribution only. Used, with the attribution
  written into the file and into every receipt.

  nothing: amphoe on 50,978 CM + 19,028 CR records, tambon on 46,270 +
  18,295; 135 tambons the address said and the pin confirms are promoted;

  a pin within 60 m of a boundary is left alone. Every district drawer and
  every ย่าน chip fills from this. River Tavern's own pin stands in ต.ริมกก,
  not the ต.เวียง Google's address string said — corrected.
  Runs at the tail of import_all; it is in the next data pass, then the
  build after that.

THE ENGINE AT THE EDGE (WO-82)
  The page's engine needs 537 MB of memory for its index; no Worker can hold
  that. So the build now writes the engine's postings as 1,024 small shard
  files (33 MB) and the Worker walks them: /api/v1/search runs searchcore
  itself — the same file the page runs — and answers in about 30 ms with the
  vocabulary in memory and only the lists a query needs fetched. Held to the
  page's engine on 18 queries: identical rankings, id by id. The results
  page asks it first, so the first rows are the RIGHT rows, ranked by the
  real engine, before the 10 MB index has even started to arrive.
  Deployed 20:35 after you logged wrangler in (version c07a3c83). The API's
  city filter is live at once; /api/v1/search says "not deployed" until the
  second content deploy lands the shards, then it answers.
