WHAT HAPPENED, from the evidence and not from a guess

  The live site is an OLDER build's bytes with a large set of paths deleted
  out of it. Proof: live /cm/food/ asks for md.js?v=aabffca9 and
  refine.js?v=02afaee0, while the tree on this disk asks for 8a539bb5 and
  e8ebfe51; live md.js is 257,091 bytes against 271,057 here. So the live
  content was not written by the build running now.

  What is missing live: index.html · 404.html · map.js · live.js ·
  explore.js · explore.css · favicon.ico · sitemap.xml · what.html ·
  toilets.html · reach.html · the whole of /cr/ · /glyphs/ · /vendor/ ·
  /api/v1/index.json. What survives: /cm/** · /data/** · md.js · refine.js ·
  robots.txt · style.css · the images · both tile archives.

  `rclone sync` is a mirror. It deletes from the bucket whatever is not in
  docs/ when it looks. Somebody's publish looked at a docs/ that did not hold
  those files — a build that had been killed part-way, or one still running —
  and the deletions followed. Nothing was hacked and nothing is lost that a
  finished build does not rewrite.

WHY BOTH EXISTING GUARDS PASSED IT — this is the part worth keeping

  1. FLOOR = 20,000 files. It is a TOTAL, and docs/cm/ alone is 77,107
     files. A tree holding only cm/ and data/ clears the floor FOUR TIMES
     OVER while missing every root page, both provinces' front doors, the
     vendored map engine and every glyph. A total count cannot see a missing
     root. It never could.

  2. The build lock. It refuses a publish while a build is ALIVE, and clears
     a lock whose process is gone — correctly, or one crash would wedge the
     repo forever. But a killed build leaves exactly what the lock stops
     protecting: a real, populated, half-written docs/. The lock guards the
     build in progress. Nothing guarded the wreckage it leaves.

  Neither guard was careless. Both asked "is anything running?" and "is this
  big?" when the question is "is this THE SITE?"

  Third finding: a publish left NO RECORD on this machine. Not when, not
  what it deleted. The most destructive thing this repo does was the only
  thing that wrote no log, so this had to be diagnosed backwards off the
  live site's own 404s.

BUILT TODAY — publish/safety.py, wired into publish/deploy.py

  a. REQUIRED PATHS. A short, certain list the site cannot be served
     without: index.html, 404.html, md.js, style.css, robots.txt,
     sitemap.xml, llms.txt, cm/index.html, cr/index.html — plus map.js, both
     vendored libraries and two glyph ranges WHEN a basemap is configured
     (an empty basemap url is a supported state, so those are conditional and
     say so). Missing any of them refuses the publish and names them.
  b. PER-SUBTREE FLOORS. cm ≥ 1,000 · cr ≥ 100 · data ≥ 20. This is the
     check the total could not do: a limb falling off is now visible.
  c. DELETION PREVIEW. Before anything is destroyed, both sides are listed
     and the difference is shown. More than 2,000 deletions stops and asks
     for --prune. Anything under vendor/, glyphs/ or api/ is refused even
     WITH --prune, because losing those does not shrink the site, it makes
     every map blank, unlabelled, or 503.
  d. SMOKE TEST AFTER THE UPLOAD. Eleven live URLs (plus four more when a
     basemap is on), including one that must return 404 so a bucket serving
     200 for everything is caught too. A failure exits non-zero and says so.
  e. A DEPLOY LOG at cache/deploy.log — when, which pid, how many deletions.
  f. The checks re-run under the lock, not only before it.
  g. tests/test_publish_safety.py, 21 checks, all green. The one that
     matters rebuilds a miniature of the outage tree and asserts it is
     refused; it also asserts that tree clears the old floor, so the hole
     stays documented in a test rather than in a memory.

  Run either half alone, no network needed for the first:
      python3 publish/safety.py           is docs/ a whole site?
      python3 publish/safety.py --smoke   is the live site answering?

  Checked against reality: run against docs/ as it stands mid-build, it
  names all twelve missing paths and the empty cr/, and refuses.

STILL OPEN — the root fix, and it is yours because it edits build.py

  R1  BUILD BESIDE, THEN SWAP. build.py wipes docs/ in place, so for the
      ~40 minutes a build takes there is a half-written site sitting at the
      published path looking publishable. Build into docs.next/ and rename
      it over docs/ at the end and a partial tree never exists where a
      publish can find it. Every guard above becomes a belt to that brace.
      Cost: a second copy on disk during the build, and an edit to build.py's
      clear_docs() — which other sessions are in constantly, so it wants a
      quiet moment rather than a race.
  R2  A WATCH ON THE LIVE SITE. `python3 publish/safety.py --smoke` is
      already the whole job; it wants a schedule and somewhere to shout.
      Not scheduled — a standing job on your machine is yours to say yes to.
  R3  NEVER DELETE ON THE ORDINARY PATH. Stronger still: make --yes upload
      only, and retire pages in a separate deliberate --prune pass. Costs
      some stale objects in the bucket; buys the property that an ordinary
      publish can never remove anything. I did not take this one — it
      changes what a publish MEANS, and the file's own docstring says
      retiring pages is wanted behaviour.
  R4  A published-tree manifest. Write the key list of every good publish to
      cache/, so "what did we lose" is answerable in one diff instead of by
      probing URLs. cache/last-published.json is a SOURCE fingerprint and is
      not this.

§12 explains how a half-built docs/ reached the live site. This is why docs/
was half-built in the first place, and it is simpler and worse.

  THE DISK WAS AT 99%. 2.1 GB free of 228 GB.

The build I was watching died at 12:39 with **exit code 120** and a traceback
that was itself truncated — "Exception ignored in <_io.TextIOWrapper
name='<stdout>'>". Exit 120 is what CPython returns when it cannot flush
stdout as it exits. The build could not finish writing its own error message,
which is why the log is nine lines long instead of several hundred.

So the chain runs: disk fills → every build dies part-way → docs/ is left
holding a real, populated, half-written site → a publish mirrors it → the
front page 404s. The guards in §12 break that chain at the last link. This
breaks it at the first.
