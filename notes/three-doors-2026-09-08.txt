3. TAGS THROUGH ALL THREE

  A tag is one word on a sign, read by the crawl (1,782 trade terms,
  go/trades). Today it is a search filter and a link on a place page.
  After this it is the pivot between the doors:

    boolean   tag=a,b (OR) · across keys AND · not=tag:x       BUILT, WO-75
    map       #z/lat/lng/shelves?tag=a,b — rows drawn are the tagged rows;
              the chip rail counts tags IN THE VIEWPORT (WO-74 L3)  NOT BUILT
    calendar  events at places carrying the tag; the tag chips on
              events.html counted against the events on screen        NOT BUILT

  THE CHIP HAS THREE SIDES. Wherever a tag is printed — a place page's
  "Listed as doing", the refine bar, the tap card — it is one chip with
  three taps: the word (→ search?tag=), [map] (→ map.html?tag=), [cal]
  (→ events.html?tag=). No new words: the two glyphs are the same two
  doors the masthead carries. Counts on the map and calendar sides come
  from the same tables the boolean already bakes (data/search_tables.json
  `trade` rows), so a tag with no pinned rows draws no map side and a tag
  with no events draws no calendar side — a door is never drawn on zero.

  DATA TO VERIFY before the map side ships: whether the 0.01° cells under
  docs/data/here/ carry the tag list per row. If not, one line in
  here_layer's cell writer. Events already carry place ids; place → tags
  is a join the build has.
