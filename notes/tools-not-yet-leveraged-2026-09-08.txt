2. SEARCH + DISCOVERY
------------------------------------------------------------------
2.1  Inverse document frequency in searchcore.js — no library
     assets/searchcore.js has no IDF term at all (grep: zero hits).
     That is the guitar bug: "buy" (261 records) weighed the same as
     "martin" (4). Fix = one dict of document frequencies shipped in
     the index and one line in the scorer. Measure first with
     xhluca/bm25s (MIT, numpy) offline against the 52 scored questions.
     Effort: hours. Risk: none. The single largest search win.

2.2  Intl.Segmenter('th') — built into every browser, 0 bytes
     Baseline since April 2024 (Chrome, Safari, Firefox 125). Gives the
     search box a Thai word cutter for free at query time; the DP
     segmenter from thapsap stays on the build side. Index both the
     segmenter's words and character 3-grams so the two cutters'
     disagreements do not cause misses. Effort: a day.

2.3  Pagefind v1.5.2 — https://github.com/Pagefind/pagefind — MIT, 5.4k★
     Now segments Thai (2.0 above). Replaces the 9.5 MB up-front index
     with per-query fragments of tens of kB, served as static files
     from R2 — the low-bandwidth design point. Node API addCustomRecord
     takes JSON records, so no HTML parsing; filters give the
     Term (count) browse for free. Cost: a Rust binary in the build (one
     command, not stdlib); its ranking is its own, not ours; no
     geosearch. Best if bandwidth outranks ranking control. Fork A.

2.4  MiniSearch — https://github.com/lucaong/minisearch — MIT, 6.1k★
     ~8 kB gz. Pluggable tokenizer (drop Intl.Segmenter in), IDF, field
     boosts, fuzzy + prefix, AND/OR/NOT, serialised index. The
     drop-in replacement for searchcore.js if we keep one index file.
     Fork A.

2.5  Orama — https://github.com/oramasearch/orama — Apache-2.0, 10.5k★
     The one browser engine with GEOSEARCH (radius + polygon on a
     geopoint field) in the same index as the text — the where-question
     (kind + place + radius) answered natively. No Thai stemmer;
     tokenizer is pluggable. Bigger migration; VC-backed and pushes a
     cloud product, JS core still Apache. Prototype one shelf first.
     Fork A.

2.6  PyThaiNLP, the parts NOT tested yesterday — Apache-2.0, 1.2k★
     https://github.com/PyThaiNLP/pythainlp — run as a one-shot script
     that writes JSON the stdlib build reads, never imported by build.py.
     - soundex(engine='prayut_and_somchaip'): Thai–English CROSS-SCRIPT
       soundex, built for exactly the transliterated-name case. Index
       the code; a query in either script hits. Also the blocking key
       for conflating a Thai sign against a Latin Overture/Foursquare
       name.
     - util.eng_to_thai / thai_to_eng: wrong-keyboard-layout rescue
       (Thai typed with the layout stuck on English). Two 100-line
       dicts, portable to JS.
     - spell: build a SymSpell deletes table from OUR 88k names + trade
       terms instead of the Thai National Corpus. ~200 lines of JS.
     - transliterate.romanize(engine='royin') as a SECOND indexed field
       beside translit.py's output, not a replacement: yesterday
       measured ours 2.3x closer to the signs, but indexing both
       catches the Wualai / Wua Lai class either way.

2.7  Thai NER — pythainlp/thainer-corpus-v2-base-model (HF, CC-BY-4.0)
     WangchanBERTa base, F1 0.85, tags PERSON / LOCATION / ORG. Run
     once offline over the 88k names: "ร้านนวดตอกเส้นป้าแดง" → ORG
     "ป้าแดง", residual "นวดตอกเส้น" becomes the offers field. That is
     the structural cure for "indexes what a place is called, never
     what it offers". Caveat on the model card: pre-tokenise with
     word_tokenize or the tags are wrong. CPU, ~an hour for 88k.

2.8  bge-m3 SPARSE head — we already run the dense head on Workers AI
     MIRACL Thai nDCG@10: dense 81.8, dense+sparse 83.3. The sparse
     output is a learned lexical weighting — the rare-word signal we
     lack. Whether @cf/baai/bge-m3 exposes sparse output is NOT
     verified (docs do not print the schema; a community request
     suggests dense-only). If not, FlagEmbedding (MIT) offline once,
     store each record's top-k sparse terms as an indexed field.

2.9  Reranker — BAAI/bge-reranker-v2-m3 (Apache-2.0, Thai ~81.7).
     The smaller bge-reranker-base is already on Workers AI. Rerank the
     top 30 only for multi-word queries. Jina's reranker is
     CC-BY-NC — skip.

2.10 ItemsJS — https://github.com/itemsapi/itemsjs — Apache-2.0, 408★
     Facets with AND/OR per facet, counts, zero-bucket hiding, similar
     items by field, "up to 100k items". Our Term (count) browse and
     the boolean-refine drawers are its facet model; would replace
     bespoke count code. Loads everything in memory — same as today.

2.11 "Similar places" needs no library: top-10 nearest by bge-m3 cosine
     within the same kind (one Vectorize query per record, offline),
     a tag co-occurrence PMI table (stdlib), a seeded per-day random
     walk. Static JSON, no tracking, works offline.

Browser-side embeddings: NOT NOW. multilingual-e5-small int8 is 113 MB,
potion-multilingual 128 MB; multilingual vocabularies make every
"small" model large. Embeddings stay at the edge.

3. MAPPING

3.1  MapLibre GL JS v6.7.0 / v6.8.0 — we vendor v5.24.0
     https://github.com/maplibre/maplibre-gl-js — BSD-3
     v6.7.0 (released 2 Sept 2026, six days ago): "Wrap Thai, Khmer,
     Burmese, Lao labels at word boundaries" via Intl.Segmenter with a
     grapheme guard so a tone mark never starts a line; and font-faces:
     a style can name the self-hosted Noto Sans Thai as a CSS
     @font-face, so text shapes in the browser and the PBF glyph-range
     fetches go away (bandwidth win). v6.8.0 (7 Sept) builds the
     segmenter lazily. Cost: a version bump + a test page of tambon
     labels; the PR itself says combining-mark positioning is still
     incomplete. Test before deploying.

3.2  Tambon POLYGONS — the largest geocoder gain available
     https://github.com/DevelopedbyWill/thailand-canonical-admin-names
     CC-BY-4.0 (data), 7,436 tambon polygons in a 7.1 MB GeoJSON, from
     OCHA COD-AB (Royal Thai Survey Dept). Same polygons:
     prasertcbs/thailand_gis (113★, no licence stated) and HDX
     cod-ab-tha. We hold tambon CENTROIDS built from our own pins
     (geocode_local.py) and distrust thin ones. With polygons: cut the
     43 CM+CR amphoe at build time; point-in-polygon every pin to get
     a verified tambon on every record; reject any parsed address whose
     tambon polygon does not contain the candidate pin (kills most
     ±3 km misses); reverse-geocode the 2,116 unpinned to a tambon.
     No village (moo) polygons exist open anywhere.

3.3  kdbush + geokdbush + flatbush — https://github.com/mourner/kdbush
     ISC. A static spatial index as ONE ArrayBuffer; KDBush.from(buffer)
     loads without rebuilding; geokdbush.around(lon, lat, n, maxKm).
     build.py writes the buffer (documented flat layout: ids + coords;
     ~1.4 MB for 88k, gzips well) to R2; the browser answers "coffee
     within 800 m of Chang Phueak Gate" in microseconds with no
     server. This is the where-question tool the parking bug asked for.
     Cost: a day matching kdbush's header layout from Python.

3.4  geojson-path-finder — https://github.com/perliedman/geojson-path-finder
     ISC, 332★, deps @turf/distance + tinyqueue. Dijkstra/A* over a
     GeoJSON line network in the browser. The 9,767-node road graph is
     already the right input; ride-planning point-to-point is a direct
     fit. Isochrones (the breathing map) need one-to-many, which the
     public API lacks — the graph object is exposed, ~40 lines of
     Dijkstra-to-all + a concave hull gives the polygon. City scale,
     not province.

3.5  maplibre-contour — https://github.com/onthegomap/maplibre-contour
     BSD-3, 286★. Contours + hillshade for Doi Suthep from one
     self-hosted DEM tileset (Copernicus 30 m → rio-rgbify → PMTiles),
     computed in the browser. DEM tiles are heavy: behind a toggle,
     capped zoom.

3.6  maplibre-offline-pmtiles — https://github.com/makinacorpus/maplibre-offline-pmtiles
     MIT, 9★, tiny. downloadMap / loadMap into OPFS; 10–100 MB packs.
     A "take Chiang Rai offline" button. Small enough to vendor if it
     goes stale. Glyphs need the service worker (fonts are already
     self-hosted).

3.7  overture-geocoder — https://github.com/brad-richardson/overture-geocoder
     MIT, active this month. A PATTERN, not a dependency: Rust Worker
     + SQLite/FTS5 shards in R2 read by range. Same stack as ours.
     SQLite FTS5's trigram tokenizer indexes Thai with NO segmentation
     at all. Shard CM/CR records + tambon + sois and answer gazetteer
     queries from the Worker in tens of ms. Complements Vectorize.

3.8  thaiaddress — https://github.com/425degree-developers/thaiaddress
     Apache-2.0, 66★, ML parser: name / tambon / amphoe / postcode /
     phone out of a raw address string, reported F1 0.94 on limited
     data. A pre-pass before geocode_local; accuracy on sois
     unverified.

3.9  Romanisation lookup: pythainlp/thai-romanization-dataset (HF,
     647k word→roman pairs, rich in ตำบล/บ้าน names) as an
     exact-match layer BEFORE translit.py's rules. CC-BY-SA-3.0: a
     shipped table derived from it is share-alike. Fork B.
     wannaphong/thai-english-transliteration-dictionary (3,868 pairs,
     CC-BY-4.0) has no share-alike.

8. FORKS — yours
------------------------------------------------------------------
A. Browser search engine. (i) Keep searchcore.js, add IDF + Intl.
   Segmenter — hours, no new dependency, index stays 9.5 MB. (ii)
   MiniSearch — a day, 8 kB, same one-file index, gets fuzzy/prefix.
   (iii) Pagefind — a Rust binary in the build, fragments the index so
   a query costs tens of kB, its ranking not ours. (iv) Orama —
   biggest migration, the only one with geosearch in-index. Worst
   case for (iii)/(iv): a ranking we cannot tune when the next guitar
   bug arrives. (i) is safe to do regardless; (ii)–(iv) are the fork.
   No expiry. Retriever-first (your 9/7 decision) makes the browser
   engine the offline + instant-name path, which argues for (i).

B. Share-alike data. The 647k-pair romanisation dataset is CC-BY-SA;
   a lookup table built from it must ship share-alike. Use it (better
   romanisation, licence line on the table) or use only the 3,868
   CC-BY pairs. No expiry.

C. Foursquare gate. One login with name + intended use, Apache-2.0
   data, then measure Thailand. Or measure on the ungated 2024 mirror
   first and decide after. Worst case: an hour spent on a source that
   duplicates Overture's 855 rows. No expiry; monthly releases.

D. Panoramax server. The first item on this list that needs a server
   (Postgres, optional GPU). You struck "purely static" on 9/7, so it
   is presentable: a self-hosted, blurred, geo-indexed photo layer
