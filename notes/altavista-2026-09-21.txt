THE TWO WAYS
==============================================================================

  SIMPLE — words, and the page must hold all of them.
    +คำ must appear · −คำ must not · "a phrase" · dermat* · title: url: site:
    ลองโชค · LUCKY sends you to the first page found.
    When every word finds nothing it widens one step at a time and says
    which step answered: words split apart (a Thai compound), any word,
    then synonyms from the fleet thesaurus (toksen → ตอกเส้น).

  BOOLEAN — AND OR NOT NEAR ( ) "…" *, a site menu, a date range.
    NOT binds tightest, then AND, then OR. NEAR = within 10 words.
    Upper-case AND/OR/NOT/NEAR in the simple box switch it on too.

FILTERING AND SORTING (added the same day, on your second ask)
==============================================================================

  Four controls, the same on both doors. On a results page they are a bar of
  links across the top, each carrying the count it leads to:

    เรียง · Sort          ตรงที่สุด Best match · ใหม่สุด Newest ·
                          เก่าสุด Oldest · ก-ฮ A–Z
    คำอยู่ที่ · Words in   ทั้งหน้า Anywhere · ชื่อหน้า Title · ที่อยู่ Address
    ปรับปรุง · Updated    ทุกช่วง Any time · 7 days · 30 days · a year
    ไซต์ · Site           every site the answer touches, counted

  On the boolean form the same four are dropdowns, with from and to dates
  instead of the presets, and 10 / 20 / 50 per page.

  Three rules it holds to, each of which cost something to get right:

  A COUNT IS THE COUNT YOU GET. The site numbers are taken with every other
  filter already applied; the date numbers with the site filter applied. A
  bucket holding the whole answer narrows nothing and is not shown — most of
  Mot Dang carries the date of the nightly build, so "7 days" and "30 days"
  are usually the same number, and showing both twice would be furniture.

  A SORT ORDERS WHAT YOU CAN REACH. Anything but relevance orders the best
  1,000 matches, which is also as deep as the pager goes, and the page says
  so when the answer is bigger. Sorting 61,000 rows to show ten would cost
  nine seconds and nobody would ever page to row 1,001.

  THE FILTERS RIDE ALONG. Every link and both boxes carry the query, the
  sort, the site, the dates and the page size, so typing a new word keeps
  your filters and a results address is a bookmark. Changing a filter goes
  back to page one, because page seven of the old answer is not page seven
  of the new one. When an answer is empty, the filters in force are named
  with a link to take each one off.

  WHAT IT COST TO MAKE FAST: sorting or counting touches up to a thousand
  scattered rows, and read from the main table those are fat rows — title,
  abstract and address — which took nine seconds on the broadest query. A
  covering index did not fix it: for a table keyed by rowid SQLite prefers
  the primary key and reads the whole row anyway. So the keys now live in
  their own narrow table, about 10 MB, and only the ten rows that survive
  the sort are read whole.

==============================================================================
HOW IT WORKS, IN A LINE EACH
==============================================================================

  fleetsearch/crawl.py reads each site's docs/ → 105k rows in 137 s.
  fleetsearch/load.py puts them in a Cloudflare D1 database (SQLite with
  full-text search) — 22 chunks, 15 min.
  publish/fleetsearch.js turns what you typed into a full-text query and
  writes the page; the site Worker routes /find to it.
  Thai is split into dictionary words on both sides with the same file
  the site already uses, and sent as a phrase.

  Tests: 39 query-language and SQL cases, 37 end-to-end cases over a local
  copy of the index with the real dictionary, 12 crawler-and-wiring checks.
  All green before each deploy. The three existing Worker suites still green.

==============================================================================
WHAT IS NOT DONE, AND THE FORKS
==============================================================================

  RELOAD. The index is a snapshot of today's builds. Reloading is two
  commands (crawl.py, load.py), but D1 does not answer queries while a
  chunk is importing — a full reload is a few minutes of /find answering
  errors. No nightly is scheduled.
    a) nightly at 04:30 Bangkok, accept the gap        (cheapest)
    b) build a delta loader first — only changed pages, no gap (a day's work)
    ⏳ if silent: (a) from 2026-09-28, the gap logged each night

  THE OLD PLACE FILTERS. advanced.html and its search.html?tag=… page are
  a second "advanced search" beside the boolean one.
    a) keep both
    b) fold the place filters (kind, area, open now, near me) into the
       boolean form as more rows
    ⏳ if silent: (a)

  RANKING. Title counts 8×, body 1×, address 2×. No site is favoured. If
  you want motdang first, or wichaa first, that is one number.

  THE DATES ARE BUILD DATES, mostly. Mot Dang rebuilds nightly, so nearly
  every page of it says it changed within the week and the "updated" filter
  cannot tell a page that really changed from one that was reprinted. It
  does separate the older sites — defiant.to still says July — and the
  bar hides a bucket that holds everything, so it shows as little as it can
  rather than pretending. Making it mean more needs the record dates the
  build already knows, which is work on the crawler, not on the search.

  NOT SEARCHED: sites with no build on this disk — ask.motdang.net,
  ai.motdang.net, Patreon, Ko-fi.
