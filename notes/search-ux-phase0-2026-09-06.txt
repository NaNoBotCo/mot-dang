1. THE SEARCH INDEX (work order item 1)
================================================================================

WHERE: build.py, the loop near "search_index.append" (around line
14230-14480). Output docs/data/index.json — 8.18 MB on disk (the
docstring still says 6.2 MB). The whole file is fetched on every query.
By the repo's own arithmetic that was 36 s at 1.5 Mbps when it was
6.2 MB; it is now about a third bigger.

FIELDS PER ENTRY
  n   Thai name (shown)
  e   English name (shown)
  a   alt names, old names, CJK names, and the RTGS reading of a
      Thai-only name — matched, NEVER shown
  c / su   category and sub-shelf codes (words looked up client-side)
  k   everything else: kind attributes, cuisine, brand, operator,
      offers, specialty, register words (trans health, ADHD, OT, the
      lens registers), every tag's two names, tambon + amphoe (Thai
      only), street, AND blurb_th + blurb_en (added 2026-09-05)
  h   opening hours string;  f   facet keys;  lat/lng

WEIGHTS AT MATCH TIME (md.js, generated by build.py)
  name  = n + e + a                      weight 1.0
  shelf = category words + sub words + k weight 0.45
  So a blurb is already BELOW the name and level with category, tags
  and address. Work-order Phase 1.1 is already the case.

TOKENIZER (assets/searchcore.js, generated from ../search-core/, a
line-for-line twin of searchcore.py, parity-gated across the fleet)
  Thai: no spaces, so every Thai query is a compound. Thesaurus first
  ("never split ร้านยา"), then mend one letter, then segment against a
  corpus dictionary (docs/data/search_segdict.txt, 383 KB). No
  character n-grams by policy.
  Latin: accent strip, a phonetic key over six romanization habits
  (Rajavej = Rachawet = Ratchavej), bounded Damerau-Levenshtein.
  Both scripts live in the same fields. There is NO query-language
  detection (work order 1.4 not built).

TIERS AND SCORE
  exact 1.0 · thesaurus 0.8 · loose 0.55 · partial 0.3
  Per term, the best (tier × field weight) across fields. Score is the
  sum times coverage squared. Rows matching every term win outright if
  any exist ("loosen by steps"). "not every word matched — closest
  first" prints when no row matched every term. That is the only thing
  the page says about what was dropped.

THE TRIGGER CASE, RE-RUN OFFLINE THROUGH THE PYTHON TWIN
  Query "Big women's shoes" → terms big, women, shoes ("'s" dropped;
  thesaurus widened big → huge, large, and also "abroad").
  306 rows (you saw 427 on 9/5; live today 396 — the index changes
  every build, so that number is not a stable target). ZERO rows match
  all three terms.

    0.64  ปุ้มปุ้ย บิ๊กไซส์   big = NAME exact 1.0 · women = k 0.45

  "big" maps to the shelf 'shopping' (so does ไซส์ใหญ่); บิ๊กไซส์ maps

5. ROMANIZATION — WHERE IT REACHES AND WHERE IT DOES NOT (your steer)
================================================================================

site's own segmentation dictionary, gloss() for the head words วัด /
โรงเรียน / โรงพยาบาล / ร้าน. It renders as an italic `.roman` mark,
labelled as a reading, never stored as a name. Its own docstring
already retires the old "no machine transliteration" ban.

WHERE IT RENDERS: name_bi() only — a Thai-only name with no Latin at
all. 7,519 CM + 3,144 CR place pages carry a reading somewhere on them
(own name or a "more like this" row). 9,884 records have a Thai-only
name.

WHERE IT DOES NOT
  trade tags   1,724 distinct Thai tags on 2,564 records; English on
               57 records (2 percent); readings on none. Today they
               print only inside the tag-join blurb — and vanish in
               English mode.

               index comment refuses the machine reading here until a

               lexicon file exists: data/curated/rtgs_lexicon.json.
  addresses    10,839 records; 1,346 contain any Latin.

  homepage / shelf pages   0 `.roman` marks on index.html or

  English blurbs   81 unglossed Thai runs, mostly street names.

6. INTAKE — HOW A FACT REACHES A PAGE TODAY (your steer)
================================================================================

Reader paths: POST /suggest (suggest.html), POST /claim (claim.html),
POST /toilet, POST /listing (the listing sheet), LINE webhook.

A suggestion's road:
  1 reader types it → 2 Worker writes KV → 3 a person runs
  importers/sync_suggestions.py (wrangler, --remote, authenticated as
  you) → 4 _incoming/suggestions.json, gitignored → 5 a person reads it
  and hand-edits data/curated/additions-*.json (or asked_new.py for a
  question) → 6 import_all.py → 7 build.py (lock) → deploy.py.
  Seven hands; steps 3, 5, 6, 7 are a human at a keyboard.

The one path that publishes itself: an owner CLAIM. applyClaim → GET
/claims → sync_claims.py → build.py "owner-claimed facts win" (~791).
It accepts contact channels and hours only (build.py ~11640).
Claims since launch: 0. Toilet reports: 0. heard.jsonl: 0.
fixes.json: 14, ten of them มดเอง.

What a place OFFERS has one structured home: attrs.offers, each entry
with a shelf key, via, seen date and url, rendered by the offers block
(build.py ~8104) with its source linked. It is written only by
importers. No form on the site writes it.
